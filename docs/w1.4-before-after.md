# Web-app backend w1.4.1: before and after pasting WebApp.gs

**Status:** ready to apply, after the review in `docs/review/` (05/11/2026).
**Applies to:** the **web-app** Apps Script project only. Never the Telegram bot's project.
**File to paste:** `WebApp.gs` w1.4.1, sent by Claude on 05/11/2026. It is also kept as `deliverables/WebApp.gs` in the build workspace (see §9 to rebuild it).

w1.4.1 replaces the w1.4 file sent earlier the same day. That file had two bugs, both fixed here (§3.4). If you still have the w1.4 file, do not paste it.

## Words used in this document

- **Screen**: a page of the phone app: *Hari ini* (today's activities), *Data*, *Laporan* (reports), *Saya* (profile, with the version line at the bottom).
- **Tab**: a sheet tab in the Google Sheet (Entries, Plans, Settings …). This document never uses "tab" for a screen.
- **Backend**: the web-app's own Apps Script project. Its single file, WebApp.gs, contains:
  - the web-app's code, `web.gs`;
  - a copy of the functions it needs from the Telegram bot's code, copied **unchanged** by `backend/build.js`.

  The backend therefore reads and writes the Sheet exactly as the bot does. "bot v1.4" in WebApp.gs means "copied from bot v1.4". The live bot is not touched.
- **Versions**:
  - backend `w1.x` ("w" for web);
  - phone app `1.x.x`;
  - Telegram bot `v1.x`.

  They are numbered separately. Backend w1.4 and bot v1.4 share a number by chance.
- **Fast read**: the optional single Google Sheets API call described in §3.1.
- **Read-only actions**: the five backend actions that never write to the Sheet:

  | Action | What it serves |
  |---|---|
  | `day` | the day view |
  | `reports` | the PDF report list |
  | `imports` | the contractor list on Hari ini |
  | `import` | one contractor tick list |
  | `pdfState` | the reading status of an uploaded contractor PDF |

## 1. Why this change exists

The team reports that changing the date in the web-app takes 10 seconds or more. This is the user's own timing on a phone, 05/11/2026; nobody has measured how that time divides up. Reading the code shows these causes:

- **The app waited for the server every time.** It kept a copy of each day on the phone but showed it only when there was no internet.
- **The backend read the Google Sheet tab by tab.**
  - One date change made about 30 small calls to Google Sheets: for each tab, its last row, its width, its header and its values.
  - The whole Entries tab was read 2 or 3 times.
  - Entries holds every activity since the project started, so this read grows with every activity added.
- **The login check** sometimes adds work. About once a minute it re-reads the WebUsers and Users tabs, while holding the script lock that saves also use.
- **The Laporan screen** asked for the report list twice on each date change.
- **Opening the app** fetched the team list and the day one after the other.
- **Apps Script start-up:** each request goes through a redirect, and the first one after the app has been idle waits for Apps Script to start. This change does not remove that time.

## 2. Goals and non-goals

**Goals**

- A date already opened on the phone shows at once.
- A date never opened shows faster than now. A pass mark is set in §6.
- Nothing the bot reads or writes changes.

**Non-goals (what does not change)**

- **The Telegram bot:** its project, code, Script properties and triggers.
- **The Sheet:** no tab or column is added, renamed or moved.
- **Saves, edits and deletes:** they use the bot's own code, unchanged.
- **The login check:** it is unchanged. Making it lock-free would need new code; revisit it if §6 shows lock waits.
- **The growth of Entries** (see §5.3).
- **The `/exec` address and deployment access** ("Execute as: Me", "Anyone"), provided step 6 is followed.
- **Logins, PINs and sessions:** everyone stays logged in.

## 3. What changes

### 3.1 Already live: phone app 1.4.0

This shipped through GitHub Pages and works with **both** the old and the new backend, because the app asks the server for nothing new.

| Behaviour | Before (app 1.3.x) | Now (app 1.4.0) |
|---|---|---|
| Opening a date seen before on this phone | Waits for the server | Shows the saved copy at once. The date pill says "Mengemas kini…" ("updating…") until fresh data arrives |
| Tapping ‹ (back one day) | Waits for the server | Shows at once, if the background pre-load has finished (below) |
| Opening the app | Team list, then the day | Both at the same time |
| Laporan screen, date change | 2 report-list requests | 1 request |
| Saved copies on the phone | One per date ever opened, never removed | The 21 dates most recently fetched; older ones are removed on each save |

Three time windows control how often the phone asks the server again. They are separate, because each guards a different thing.

- **1 minute.** If a date was fetched in the last minute, for example by the pre-load, changing to it sends no new request.
- **3 minutes.** After each date change, the phone fetches the day before in the background, unless that day was fetched in the last 3 minutes. The longer window stops quick back-and-forth taps from re-fetching.
- **20 seconds.** The report list for a date is reused for 20 seconds.

On top of these, if a request for a date is already on its way, a second one for the same date waits for it instead of sending another.

These timings come from the local preview, with every request slowed on purpose to 3 seconds:

| Action | Time until the list showed |
|---|---|
| Back one day, back again, forward one day | 0.1 s or less |
| Reopen the app | 0.1 s or less |
| A date never opened | 3 s (the slowed request itself) |

### 3.2 When you paste WebApp.gs w1.4.1: reading the Sheet

For the five read-only actions, each Sheet tab is read once per request. Before, it took several calls per tab and repeated reads of Entries.

| For one date change on the Hari ini screen | Before (w1.3.x) | After, fast read **off** | After, fast read **on** |
|---|---|---|---|
| Calls to Google Sheets for the day's tabs | About 30 | About 8 (one per tab) | 1 |
| Entries tab read | 2–3 times | Once | Once (inside the single call) |
| Settings and Categories | Bot's code (5-minute cache) | Bot's code, unchanged | Bot's code, unchanged |
| Values the rest of the code sees | — | Identical to before | Identical to before (exceptions in §5.2) |

**How a read works in w1.4.1**

1. A request for one of the five read-only actions starts a per-request store of rows.
2. With the fast read on, one Sheets API call fills it with that action's tabs.
3. The bot's row reader takes each tab from the store, or reads it once and keeps it.
4. The store is cleared when the request ends, even after an error.
5. Every other request, and the tabs WebUsers, Users, Settings and Categories, always use the bot's own reader.

**The rule for maintainers:** an action may be added to the read-only list only if it never writes to the Sheet. The list is `WEB_READS` in WebApp.gs.

### 3.3 Also included, if w1.3.1 is not live yet

WebApp.gs carries every earlier change. If the project still runs w1.3, pasting w1.4.1 also brings in w1.3.1: the "Laporan kontraktor" (contractor report) card on Hari ini shows only on the date its report covers.

### 3.4 Fixed since the w1.4 file (found in review)

1. **Settings and Categories are no longer in the fast read.** In w1.4, with the fast read on, a time typed by hand into Settings went wrong. For example, `8:00` typed into `TIME_START_U1`, which Google Sheets stores as a time, came back as the number 0.333…. The bot then cached that number for 5 minutes, for every action, so the WhatsApp text showed "Time Start: 0.33…". Both tabs are now always read by the bot's own code. A test reproduces the w1.4 bug and passes with the fix.
2. **The setup log now separates first install from upgrade.** In w1.4 its last line said "Deploy → New deployment", which is wrong for an upgrade. It now prints both cases.

## 4. Alternatives considered

| Option | Why not chosen |
|---|---|
| Cache the finished day view on the server | The bot is a separate project and writes the Sheet directly, so the web-app cannot clear the cache when the bot writes. Apps Script's cache also holds at most 100 KB per value, and Entries keeps growing |
| Split or archive Entries, or add a per-day summary tab | Changes the bot's tabs, which breaks the non-goal in §2 |
| One combined server action for the whole screen | Changes what the app asks for, so old and new app versions would no longer work with both backends |
| Phone-side changes only | Shipped (§3.1), but a date never opened stays as slow as before |
| **Backend: each tab read once, fast read optional (chosen)** | Uses the bot's own code for every value. The fast read is added only if §6 shows it is still needed |

## 5. Risks and limits

### 5.1 Expected effects

- **Possible permission prompt.** Adding the Sheets API service (step 8.8, optional) can make Google ask for permission again. The access is the same Sheets access the project already has.
- **A saved copy can be out of date for one refresh.** While "Mengemas kini…" shows, the screen may still list an activity that someone else changed or deleted. Wait for it to clear before editing.
  - Saving over an activity someone else changed replaces their change. This is the same as before w1.4.
  - Saving on an activity that was deleted shows an error, and your typed text stays in the edit screen.
  - How long the refresh takes depends on the backend: on w1.3.x it is as slow as a date change used to be.
- **More requests.** The background fetch of the previous day adds at most one request per date change.

### 5.2 Where the fast read can differ (only if you turn it on)

The Sheets API returns dates as serial numbers (days since 30/12/1899). The backend turns them back into the bot's date text only in date columns:

- `work_date`, `plan_date`, `date`, `arrived_date` and `report_date`;
- a column named exactly `at`, or one whose name ends in `_at` (`received_at`, `created_at` …). A column such as `format` does not count.

A value below 367 becomes a time of day.

- **A date typed by hand into any other column** reads as a number with the fast read on. For example, "9/10" in a material's name, which Google Sheets turned into a date, reads as 46304. Without the fast read it reads as "2026-10-09 00:00:00". The bot itself writes these cells as text, so this happens only after hand edits in the Sheet. Settings and Categories, the tabs most often edited by hand, are excluded (§3.4).
- **A plain number in a date column** would read as a date. The bot writes text, not numbers, into every date column listed above.

### 5.3 Limits

- **Entries still grows.** w1.4.1 removes repeat reads but still reads the whole Entries tab once per request. The next step is due when the Apps Script execution time for `day` (see §6) passes 6 seconds. The right next step is not decided; most options touch the bot's tabs (§4). The current row count is not known: it is the last row number on the Entries tab.
- **Sheets API read allowance (fast read only).** The backend runs as you, so every teammate's reads count against your account's Sheets API allowance, which is 60 read requests per minute.
  - Each date change uses at most 2 (the day, plus the background fetch of the previous day).
  - A Laporan visit uses 1.
  - While a contractor PDF is being read, its status is checked every 5 seconds: 12 per minute per waiting phone.
  - So the 5 people on the PIC list browsing at the same time stay under 60, unless several upload contractor PDFs at once.
  - Over the limit, that request falls back to reading tab by tab. It is slower, but nothing breaks.
- **Apps Script runs at the same moment.** Consumer accounts allow about 30. This was not measured. If it is exceeded, phones show "Ralat pelayan" (server error) or stay on "Mengemas kini…". Retry after a minute; if it repeats at peak times, report it.

### 5.4 Security

No change. The deployment still runs as you, with access for anyone who has the `/exec` address. Every request still needs a valid login. The optional service uses the Sheets access the project already has.

### 5.5 What was tested, and what was not

- The tests run the real bot code and the backend against the bot's simulator. They compare all five read-only actions with the fast read on and off and get identical results. This includes:
  - a date and time typed by hand into Entries' `work_date` and `received_at` columns;
  - a time typed by hand into Settings.
- The simulator's version of the Sheets API is based on Google's documentation; it is not the real service. The real speed, the permission prompt and the read allowance can only be confirmed live (§6).

## 7. Rollback

Apps Script keeps every deployed version, so going back is a menu choice, not a re-paste.

- **Fast read only** (if you turned it on, and check 6.4 or 6.5 shows a difference): Services → Google Sheets API → ⋮ → Remove, then deploy a new version (step 8.6). The backend then reads each tab once, through the bot's code.
- **Anything else:** Deploy → Manage deployments → ✏️ → Version: choose the number you wrote down in step 8.1 → Deploy. The `/exec` address stays the same.
- **The phone app:** nothing to do. App 1.4.0 works with the older backend.

## 8. Steps to apply (engineer, on a laptop, about 15 minutes)

All steps are in the **web-app** Apps Script project: the one whose deployment URL (Deploy → Manage deployments) matches `api:` in `app/config.js`. Not the bot's.

1. **Record the starting point.**
   - In Deploy → Manage deployments, write down the current **version number**.
   - In **Executions**, write down the duration of the last few `doPost` runs.
   - On a phone, pick a date never opened on it (for example 3 weeks ago), time from tap until the list shows, and write it down.
2. **Paste.** Open `Code.gs`, replace its whole contents with WebApp.gs w1.4.1, and save.
   - Check line 4: it says `from web.gs + HLEP DPR Bot v1.4`.
   - Search for `WEB_VERSION`: it says `'w1.4.1'`.
3. **Do not add the Sheets API service yet.** It is optional (step 8.8).
4. **Run `setup`.** In the function list choose `setup`, then **Run**. Allow access if Google asks. The log shows:
   - `✅ Web-app backend ready (w1.4.1, bot code v1.4).`
   - `Fast read (Google Sheets API service, optional): off – the Google Sheets API service is not added …` This is expected at this stage.
   - Two `NEXT` lines. Follow **NEXT – upgrade**. The "first time" line is only for a brand-new project.
5. **If the "ready" line is missing**, the log shows an error instead. Stop, do not deploy, and send the log.
6. **Deploy a new version.** Deploy → **Manage deployments** → ✏️ (edit) → Version: **New version** → **Deploy**.
   - Do not choose "New deployment". That creates a second `/exec` address. The app keeps using the old one, and so never gets w1.4.1.
7. **Check.** Reload the app on one phone and run every check in §6.
8. **Optional, only if 6.2 or 6.3 is still too slow: turn on the fast read.**
   1. In the editor's left sidebar: **Services** → **＋** → **Google Sheets API**, version **v4**, identifier **`Sheets`** → **Add**.
   2. Run `setup` again. The fast-read line should say `on`.
   3. If it says `off – …`, the text after the dash gives the reason:
      - "not added": the service is missing, or its identifier is not `Sheets`.
      - "the call failed: …": permission was refused, or, if the project uses its own Google Cloud project, the Sheets API is not enabled there.
   4. Fix the reason and run `setup` once more. If it is still `off`, stop here and leave it off. The web-app works without it.
   5. Deploy a new version (step 8.6) and repeat checks 6.2–6.5.

## 9. Code changes (maintainer reference)

All files are **modified**, and every change is committed to `main`. The code comments explain the details; this list gives the points a maintainer must know.

| File | Change |
|---|---|
| `backend/build.js` | `RENAME = { rows_: 'botRows_' }`: the bot's row reader is copied unchanged under the name `botRows_`, because `web.gs` defines its own `rows_` |
| `backend/src/web.gs` | `WEB_READS` lists the five read-only actions and their tabs. Settings and Categories are left out (w1.4.1). `webRoute_` starts the per-request store for those actions and always clears it. `rows_` uses the store, otherwise the bot's `botRows_`. WebUsers, Users, Settings and Categories always use `botRows_`. Any fast-read error falls back to reading tab by tab |
| `backend/src/web.gs` (w1.4.1) | `setup` prints the fast-read state with its reason, and separate first-install and upgrade `NEXT` lines |
| `app/app.js` | Saved copies (21), background fetch of the previous day, sharing a request already on its way, "Mengemas kini…", report list reused for 20 s, team list and day fetched together |
| `app/sw.js` | Cache name `hlep-dpr-1.4.0`, so phones load the new app files |

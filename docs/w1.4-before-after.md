# Web-app backend w1.4: before and after pasting WebApp.gs

Status: ready to apply · Date: 05/11/2026 · Applies to: the **web-app** Apps Script project only (never the Telegram bot's project)

## 1. Why this change exists

Changing the date in the web-app takes 10 seconds or more. Two things cause most of that wait.

- **The app waits for the server every time.** It keeps a copy of each day on the phone, but showed it only when there was no internet.
- **The backend reads the Google Sheet tab by tab.** One date change opened about 10 tabs (Entries, Plans, Progress, Materials, Manpower, Days, Imports, PdfFiles, plus Categories and Settings when their 5-minute cache had run out). It read the whole Entries tab 2 or 3 times. Each read is a separate trip from Apps Script to Google Sheets. Entries holds every activity since the project started, so this part gets slower every month.

Smaller causes:

- The Laporan tab asked for the report list twice on each date change.
- On opening the app, the team list and the day were fetched one after the other instead of together.
- Apps Script itself adds about 1–3 seconds per request: a redirect, plus a "cold start" after the app has been idle. No code change removes this.

## 2. What is already live (app 1.4.0), before you paste anything

The phone side shipped through GitHub Pages and works with the backend you have now (w1.3 or w1.3.1). The app asks the server nothing new, so old and new versions work together in both directions.

| Behaviour | Before (app 1.3.x) | Now (app 1.4.0) |
|---|---|---|
| Opening a date seen before on this phone | Waits for the server | Shows the saved copy at once. The date pill says "Mengemas kini…" until fresh data arrives, then redraws |
| Tapping ‹ to yesterday | Waits for the server | Yesterday was fetched quietly in the background, so it shows at once (if fetched in the last 3 minutes) |
| Opening the app | Team list, then the day (one after the other) | Both at the same time |
| Laporan tab, date change | 2 report-list requests | 1 request; the result is reused for 20 seconds |
| Saved copies on the phone | One per date ever opened, never removed | The newest 21 days; older ones are removed on first launch of 1.4.0 |

Measured in the local preview, with every request slowed to 3 seconds: ‹, ‹ again, › and reopening the app each showed the list in 0.1 seconds or less. A date never opened on that phone still waits for the server, and that wait depends on the backend below.

## 3. What changes when you paste WebApp.gs w1.4

### 3.1 Reading the Sheet

| | Before (w1.3.x) | After, Sheets API service **off** | After, Sheets API service **on** |
|---|---|---|---|
| Trips to Google Sheets for one date change (home tab) | About 30 small calls (each tab: last row, width, header, values; Entries twice or three times) | One call per tab, each tab once | **One call** for all the tabs the page needs |
| Entries tab read | 2–3 times | Once | Once (inside the single call) |
| Rows the rest of the code sees | The bot's `rows_` result | Same values, same row numbers | Same values, same row numbers (see the exceptions in 4.3) |

"Read-only requests" means only these five actions: the day view, the report list, the contractor list, one contractor tick list, and the PDF reading status. Every save, edit and delete still reads and writes tab by tab with the bot's own code, unchanged.

### 3.2 Also included, if not pasted yet

WebApp.gs is one file that carries every earlier change. If the project still runs w1.3 (not w1.3.1), pasting w1.4 also brings w1.3.1: the "Laporan kontraktor" card shows only on the date its report covers.

### 3.3 What does not change

- The Telegram bot: its project, code, Script properties and triggers are not touched.
- The Sheet's tabs and columns: nothing is added, renamed or moved.
- The `/exec` address in `app/config.js`, as long as you deploy a **new version of the existing deployment** (step 7.4), not a new deployment.
- Logins, PINs and sessions: everyone stays logged in.

## 4. Risks and open questions

### 4.1 Things that will happen

- **Permission prompt.** Adding the Google Sheets API service can make Google ask for permission again when you run `setup`. The access is the same Sheets access the project already has.
- **Brief stale screen.** A saved copy can show an activity that someone else changed or deleted since. It is replaced as soon as the refresh arrives, usually a few seconds. If you tap an activity before then, the edit screen opens with the old text. Saving on an activity that was deleted meanwhile shows an error; nothing is lost.
- **More requests to Apps Script.** Pre-loading yesterday adds one request per date change. Requests seen in the last minute are not repeated, so day-by-day browsing does not double the count.

### 4.2 Limits that could bite

- **Sheets API read limit.** The backend runs as you ("Execute as: Me"), so every teammate's reads count against your account's Sheets API read allowance. Google publishes it as about 60 read requests per minute per user. With the service on, each day view is one read request. If the team goes over the limit, the API refuses the call and the backend falls back to reading tab by tab for that request: slower, not broken. A test covers this fallback, using a simulated refusal.
- **Apps Script running at the same time.** Consumer Google accounts have a limit of about 30 Apps Script runs at the same moment. Pre-loading adds load at busy times (for example 5 pm, when everyone updates). Not measured.

### 4.3 Where the fast read can differ from before

The Sheets API returns dates as numbers ("serial numbers"), not as date objects. The backend turns them back into the bot's date text only in date columns: `work_date`, `plan_date`, `date`, `arrived_date`, `report_date`, and any column whose name ends in `at` (`received_at`, `added_at`, `created_at` …).

- **A date typed by hand into another column**, for example "9/10" in a material's `item` cell that Google Sheets turned into a date, would read as a number (46304) with the service on. Before, it read as "2026-10-09 00:00:00". Neither is what the person meant. The bot writes text in these cells, so this only happens after hand edits in the Sheet.
- **A plain number in a date column** would be read as a date. No such case is known in the bot's tabs.

The tests compare the day view, the report list and the contractor list with the service on and off. They include a hand-typed date and time in Entries, and the results are identical.

### 4.4 What was not tested

The tests ran against the bot's simulator, not against your Google account. The real speed gain, the permission prompt, and the read limit can only be confirmed live.

## 5. How to check it worked

1. The `setup` log line reads `Fast read (Google Sheets API service): on`.
2. On your phone, Saya shows `HLEP DPR web-app 1.4.0 · backend w1.4 · bot v1.4`.
3. Pick a date you have **not** opened on this phone (for example two weeks ago). Time it before pasting and again after. Expect a clear drop, but not to zero: the Apps Script start-up remains.
4. Open the same day in Telegram (`/semak dd/mm/yyyy`) and in the web-app. The same activities show in both.

## 6. Rollback

Apps Script keeps every deployed version, so going back is a menu choice, not a re-paste.

- **Fast read misbehaving only:** remove the service (Services → Google Sheets API → ⋮ → Remove), then deploy a new version. The backend reads tab by tab again: once per tab, without the single call.
- **Anything else:** Deploy → Manage deployments → ✏️ → Version: choose the previous number (the one before today's) → Deploy. The `/exec` address stays the same.
- **The app on the phone:** needs nothing. App 1.4.0 works with the older backend.

## Detailed Implementation Plan

### 7. Steps to apply (engineer, on a laptop, about 10 minutes)

1. **Keep a copy of the current backend.** In the web-app Apps Script project, open Deploy → Manage deployments and write down the current version number. This is your rollback point (section 6).
2. **Paste.** Open `Code.gs` in the **web-app** project (title "HLEP DPR Web-app", not the bot). Select all, delete, paste all of the new `WebApp.gs`, Save. Check the first lines say `Built 2026-11-05 … HLEP DPR Bot v1.4`.
3. **Add the Sheets API service.** Left side → **Services** → **＋** → **Google Sheets API** → **Add**. Keep the identifier `Sheets` (the code looks for exactly that name).
4. **Run `setup`.** Function list → `setup` → Run → allow access if asked. The log must show:
   - `✅ Web-app backend ready (w1.4, bot code v1.4).`
   - `Fast read (Google Sheets API service): on`
   If it says `off`, step 3 did not take effect: check the identifier, save, and run `setup` again.
5. **Deploy a new version.** Deploy → **Manage deployments** → ✏️ (edit) → Version: **New version** → Deploy. Do **not** choose "New deployment": that creates a new `/exec` address and the app would stop reaching the backend.
6. **Reload the app** on one phone and run the checks in section 5.
7. **Tell the team** to close and reopen the app once. Their saved copies fill up as they use it.

### 8. Code changes in this version (for whoever maintains it)

| Where | Change |
|---|---|
| `backend/build.js` | `RENAME = { rows_: 'botRows_' }`: the bot's `rows_` is copied unchanged under the name `botRows_`, because web.gs defines its own `rows_` |
| `backend/src/web.gs` · `webRoute_` | For actions listed in `WEB_READS`, start a per-request snapshot before the handler and always clear it after (`finally`) |
| `backend/src/web.gs` · `webSnapStart_` | One `Sheets.Spreadsheets.Values.batchGet` for the action's tabs (`UNFORMATTED_VALUE`, `SERIAL_NUMBER`). Any error → empty snapshot, tabs then read one by one |
| `backend/src/web.gs` · `rows_` | Outside a read-only action, or for tabs not in `WEB_SNAP_TABS` (WebUsers and Users are never included) → the bot's `botRows_`. Inside: one `getDataRange().getValues()` per tab, kept for the rest of the request; each caller gets fresh copies of the rows |
| `backend/src/web.gs` · `webSnapRows_` / `webCell_` | Build the same row objects as the bot's `rows_` (header width = widest row, `_row` from 2, `normVal_` on each cell; date serials in date columns turned back into text) |
| `backend/src/web.gs` · `setup` | Logs whether the fast read is on (`webFastCheck_` makes one tiny read) |
| `app/app.js` | `useSaved`, `keepDay` (21 days, `dayKeys`), `tidySaved`, `loadDay(date, quiet, shared)` shares a request already in flight, `preload`, date pill "Mengemas kini…", `loadReports(force)` with 20-second reuse, meta and day fetched together |
| `app/sw.js` | Cache name `hlep-dpr-1.4.0`, so phones pick up the new app files |
